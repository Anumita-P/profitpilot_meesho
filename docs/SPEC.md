## 0.1 What the original deck said vs. what the research concluded

| Original deck claim | Research verdict (PDF) | Prototype treatment |
|---|---|---|
| "Price the kept sale" | Strong framing, mathematically incomplete | Headline stays; engine models the **full order lifecycle** |
| Contribution/impression = P(order)×(net − cost) | Order is not the terminal event; double-count risk | Replace with event-tree expectation (Section 16) |
| ₹399 kurti keeps ₹30; ₹65–150 / ₹140–220 / ₹73 costs | Illustrative, unsourced | Kept as **Illustrative** inputs, labelled, editable |
| "64% delivery", "58.8% NMV/GMV" mixed | Different metrics | Only 58.8% NMV/GMV is used, as motivation, footnoted |
| "Capital turns ~10×" | Arithmetic inconsistent (13–17×) | Working capital computed from explicit settlement + return-cycle days |
| 1,842 comparable listings, fit=53%, 70% feed, ₹70 cr | Unsupported | **Removed.** Evidence count is computed from our synthetic data |

| "Meesho protects the floor" / guarantee | Risky wording | UI says "enforces a seller-selected guardrail" |
| "Pricing → business brain" | Roadmap vision | Roadmap slide only |
| "If floor > ceiling, don't force a price" | Best idea in the deck | **Becomes the centerpiece** (No-Feasible-Price + Reverse Pricing) |
| "Diagnose before you discount" | Strong, keep | Becomes "Why are sales low?" |

## 0.2 The eight answers the brief asks for

**A. Final product thesis.** ProfitPilot helps a marketplace seller choose the intervention — price, bundle, packaging/parcel, listing quality, payment mix, or inventory action — that maximises **risk-adjusted retained contribution** under real marketplace constraints, and says plainly when price is *not* the right lever.

**B. Core user.** A small-to-medium Meesho apparel seller with 20–200 active catalogs, thin margins, frequent COD orders, meaningful RTO/return exposure and limited working capital, with little pricing/analytics expertise. Persona: **Sunita**, a Jaipur kurti seller (persona name is from the original deck; all her data is synthetic).

**C. Core problem / decision.** "My listing is getting orders — but am I actually making money, and if not, should I change the price or something else?"

**D. Core intervention.** ProfitPilot (1) takes the seller's goal, (2) predicts the full order lifecycle for the SKU at each candidate price, (3) computes expected retained contribution, (4) checks constraints, (5) decides whether **price alone** can hit the goal, (6) if not, searches non-price interventions and combinations, (7) recommends the best feasible one, (8) explains why and shows uncertainty. **Recommendation-only; the seller decides.**

**E. Strongest differentiator.** A **counterfactual, return-aware intervention optimiser with an explicit "no profitable price" diagnosis.** Mechanism-level, not interface-level: price moves COD mix → RTO/return → retained contribution, and the system can conclude "change the parcel, not the price".

**F. Prototype centerpiece.** **Reverse Pricing + What-if Simulator** (PDF §12.1): judge sets ₹60 target → moves slider → sees *"No price in the current market corridor meets your target."* → clicks **Find another lever** → sees packaging/bundle/listing options → picks one → the simulator shows the target becoming feasible.

**G. Mathematical logic that must be implemented** (Section 16): the lifecycle event-tree contribution per impression; price-dependent COD share; payment-conditional RTO; payment-conditional return probability; volumetric/parcel freight; working-capital cost; risk-adjusted contribution (mean − λ·uncertainty); constraint set; reverse-pricing search over price × intervention grid; confidence rule; sensitivity at ±50%.

**H. Claims and features that must NOT be implemented (kept as roadmap):**
- No reinforcement learning / autonomous repricing / free-running bandit. (Roadmap card only.)
- No buyer-level or personalised pricing.
- No claim that historical data reveals causal elasticity (demo uses a synthetic causal environment; fitted estimates labelled *associational*).
- No ₹70 crore, "1,842 listings", "fit = 53%", "70% from feed", "10× capital turns", "64% delivery" claims anywhere.
- No claim of Meesho internal API access, no Meesho fact from synthetic data.
- No LLM. Explanations are template + decomposition based.
- Full portfolio/assortment optimiser, causal forests, simulated bandit rollout: P2 / roadmap.

# 1. EXECUTIVE PRODUCT DEFINITION

**Name:** ProfitPilot · **Surface:** Meesho Supplier Panel add-on (prototype; not affiliated with Meesho's real systems).
**One-line pitch:** *Not "what price?" — "what should you change to actually keep ₹60 per sale?"*
**30-second judge comprehension path:** open Demo Mode → "No profitable price" → infeasible banner → **Find another lever** → three ranked options with numbers → **Why?** → event tree.
**Deliverable:** runnable full-stack web app (React + FastAPI + SQLite), offline-capable, seeded with synthetic data, three role views.

# 2. FINAL PRODUCT THESIS (UI copy version)

> **A sale is not an order.** It is a lifecycle — dispatch, delivery, return, cash. ProfitPilot prices the *kept* sale, and when no price works, it changes the economics instead.

Three principles on the landing screen: **1. Price the kept sale. 2. Diagnose before discounting. 3. If no price works, change the economics.**

# 3. TARGET USERS

| Role | Priority | What they do | What they must never see |
|---|---|---|---|
| **Seller** (Sunita) | P0 | Manage SKUs, set goal, simulate, get recommendation, save it | Other sellers' data, employee/model admin, customer PII |
| **Meesho employee** | P1 | Aggregate intervention performance, guardrails, model health, experiments | Individual customer PII, raw seller secrets beyond aggregates |
| **Customer** | P2 | See listed price/delivery/offer transparency for one SKU | Any seller economics |

# 4. CORE USER JOURNEY

```
Demo login (Seller)
 → 1 Catalog (choose SKU)
 → 2 Set goal (₹/kept order, orders/day, max return/RTO, cash)
 → 3 Economic snapshot (Estimated)
 → 4 What-if simulator (slider + 3 curves)
 → 5 Verdict: price can / cannot reach goal
 → 6a can: recommended price + explanation
 → 6b cannot: "No feasible price" → Find another lever → ranked interventions
 → 7 Why? (event tree, drivers, uncertainty, what would change this)

```

# 5. PRODUCT ARCHITECTURE

```
Browser (React + TS + Vite)
   │  HTTPS/JSON, JWT (httpOnly cookie), CSRF-safe SameSite
   ▼
FastAPI  ── api/ (routers, schemas, deps: auth, rate-limit, RBAC)
   ▼
services/ (business logic: goals, simulation, verdict, interventions, reverse pricing, diagnosis, explain)
   ▼
ml/ (fitted sklearn models + calibrated parametric ground truth) · optimization/ (grid + constraints)
   ▼
SQLite via SQLAlchemy (users, sellers, skus, observations, goals, simulations, recommendations, audit_logs, …)
```

**Two-layer truth model:** (1) **World simulator (ground truth)** — parametric functions generate the synthetic dataset, never called by seller-facing API. (2) **ProfitPilot models** — interpretable models fitted on the synthetic data; the product uses these. Because the world is known, tests check the product *recovers* the hidden optimum.

# 7. SCREEN-BY-SCREEN SPECIFICATION

Design rule for every screen: one dominant answer at the top (large type), supporting detail below, progressive disclosure. Max **4 numbers** at primary size per screen.

## 7.1 Login (`/login`)
- Product name; three principles; four demo login tiles. Banner: *"Demo environment · all data is synthetic · not connected to Meesho systems."*
- Click tile → `POST /api/auth/demo-login {persona}` → JWT cookie → redirect by role.
- States: loading spinner on tile; error toast if API down ("Can't reach the server. Retry").

## 7.2 Catalog (`/seller/catalog`)
- Header "Your catalog" + summary sentence ("3 of 8 listings may be losing money after returns"), then 3-column grid of SKU cards (max 12).
- **SKU card:** generated product image (SVG illustration by category; no external images), name, price, orders/day, return+RTO rate, contribution per kept order (Estimated), status pill **Healthy** (green) / **Watch** (yellow) / **Losing money** (red) — icon + text, not colour-only.
- Click → `/seller/sku/:id/goal`. Filter chips: All · Losing money · Watch · Healthy. Sort: contribution, orders.
- Empty state: "No listings yet. Load demo catalog" (`POST /api/demo/reset`).

## 7.3 SKU Workspace shell
Sticky header: image + name + price + **Goal chip** + step tabs **Goal → Snapshot → Simulate → Levers**. Right-aligned secondary links: Reverse pricing, Why are sales low?, History.

## 7.4 Goal (Step 2)
Four large inputs (react-hook-form + zod):
1. **Target retained contribution** (₹/kept order) — default 60, range ₹0–₹1,000.
2. **Minimum daily orders** — default 20, range 1–500.
3. **Max acceptable return + RTO** — slider 5–40%, default 15%.
4. **Working capital available (optional)** — ₹, default ₹75,000, "No limit" toggle.
Plus **Seller mode** segmented control **Margin · Growth · Cash · Clear** and a collapsible **Guardrails** panel (read-only chips: never below floor · corridor · max price move 10%/12% per recommendation · no buyer-level pricing · recommendation-only).
- Inline validation + `aria-describedby`; Save disabled until valid; debounced (400ms) `POST /api/goals/preview` → verdict chip; Save → toast "Goal saved".

## 7.5 Snapshot (Step 3)
Left hero: expected contribution per kept order at current price, big number with range and confidence badge ("₹71 · range ₹66–₹76 · Confidence: Medium · **Estimated**"). Right: "Where each ₹ goes" **waterfall** (list price → GST → product → packaging → forward freight → payment+ads → expected return/RTO loss → contribution). Below: expected orders/day, retained orders/day, return+RTO rate, NMV/day, working capital tied. Footnote: *"Unit costs are Illustrative seller inputs. In production these come from the seller's ledger."*

## 7.6 Simulator (Step 4) — THE CENTERPIECE
- Price slider ₹329–₹499 (step ₹1; arrows ±1, PageUp/Down ±10), markers **Current** (grey) and **Recommended** (purple), shaded **market corridor band** ("Market corridor ₹349–₹429 (Synthetic)"); outside corridor → hatched track + tooltip "Outside corridor — extrapolation, confidence drops".
- **Left panel — 11 metrics in 3 groups:** order probability · expected orders/day · COD share · RTO · return rate · retained orders/day · NMV/day · contribution/kept order · contribution/impression · working capital · risk-adjusted contribution. 150 ms number tween. Primary emphasis on contribution/day and retained orders/day.
- **Right panel — interactive chart** (Recharts ComposedChart, x = price): Curve 1 expected orders/day (blue, left axis); Curve 2 retained contribution/day (purple); Curve 3 risk-adjusted contribution/day (dashed) with uncertainty band. Vertical reference lines Current / Recommended; shaded corridor; tooltip with exact values; auto-annotation when argmax(orders) ≠ argmax(contribution): *"Highest orders ≠ highest retained contribution."*
- **Constraint chips** under chart (✓/✗ + text): Contribution floor · Volume floor · Return/RTO cap · Corridor · Cash · Confidence.
- **Performance:** `POST /api/simulate/curve` returns the full ~171-point grid once; slider scrubbing interpolates client-side; on release call `POST /api/simulate/point`.
- **CTA:** "Can price reach my goal?" → Levers tab.

## 7.7 Levers / Verdict (Step 5–6)
`POST /api/recommendation` returns one of four verdicts; the verdict is the page title:

| Verdict | Title | Content |
|---|---|---|
| `PRICE_WORKS` | "A price change can reach your goal" | Recommendation card (What / Why / Expected impact / Risk / What would change this) + constraint checklist |
| `PRICE_INFEASIBLE` | **"No price in the current market corridor meets your target."** | Shortfall line ("Best in-corridor: ₹53 per kept order — ₹7 short"), then **"ProfitPilot found 3 other ways to improve the economics."** + ranked intervention cards |
| `NEEDS_EVIDENCE` | "Not enough evidence to recommend a price confidently" | "We found only 8 comparable observations." + widen corridor / similar SKU / two-arm test |
| `NOT_A_PRICE_PROBLEM` | "Price is probably not your main problem" | Diagnosis card (links to §7.9) |

**Intervention card** (max 3 shown, "See all 7" expander): title, badge (Feasible ✓ / Near-miss ~ / Violates guardrail ✗), three big numbers (contribution per kept order, orders/day, return+RTO), confidence badge, **Trade-offs** (2 bullets), **Constraints**, **Why recommended**, buttons **Simulate this** / **Save recommendation**.
## 7.8 Reverse Pricing
Entry: **"What do I need to change to make ₹60 contribution possible?"**. Form pre-filled from the goal; optional inventory units and stock age. Result: **ranked feasible solutions table** (≤6 rows): solution, price, contribution/kept, orders/day, return+RTO, inventory needed, cash needed, score. Row expand → **Why this solution?** with elimination narrative. Objective and weights shown transparently (§15.4).

## 7.9 Why are sales low? (diagnosis)
Funnel (impressions → clicks → orders → delivered → kept) benchmarked against synthetic comparables; then a verdict card such as **"Price is probably NOT your main problem"** with bottleneck (e.g. Listing image), evidence (2–3 bullets), recommended action, expected effect (Estimated). Categories: Price · Listing/Image · Rating · Reviews · Inventory · Return risk · COD mix · Delivery · Product-market mismatch (last only when all other signals are normal; low confidence).

## 7.10 Model / Intelligence view (`/seller/model`, P1)
Vertical flow of 10 nodes (§14.6) as product-like cards with animated dotted connectors. Click a node → right drawer: What it predicts · Inputs · Output for this SKU · Confidence · Example interpretation · Main drivers (top 4 with direction). Toggle "Show technical detail" reveals model type, calibration error, training rows (Synthetic).

## 7.11 History
Saved recommendations (timestamp, SKU, intervention, expected contribution, status **Saved / Applied (simulated) / Rolled back**). "Roll back" demonstrates the guardrail (audit event; no external effect).

## 7.12 Demo Mode
Floating chip → panel with 5 scenario cards (§23). Choosing one calls `POST /api/demo/scenario/{id}` (selects seller, SKU, goal, mode) then navigates. "Reset demo data" link.

## 7.13 Employee views (P1)
- **Overview:** 4 numbers (recommendations generated, adoption %, estimated retained-contribution uplift, estimated NMV effect) + uplift-by-intervention chart. All **Synthetic — simulated rollout**.
- **Interventions:** aggregate table by intervention type (count, mean ΔContribution, mean Δreturn/RTO, share violating guardrails).
- **Guardrails:** live counts (blocked for below-floor, price move > cap, low confidence, corridor).
- **Model health:** calibration error, AUC/log-loss on held-out synthetic data, drift indicator (simulated), model version.
- **Experiments:** design card for the proposed randomised price test (2–3 arms, opt-in, min sample, rollback rule) + mocked, clearly-labelled result table. No PII beyond seller ID.

## 7.14 Customer view (P2)
One page: product, listed price, delivery estimate, payment options (prepaid incentive if selected), return policy. Callout: *"Everyone sees the same price for this listing. Prices are not personalised."* No seller economics.

# 9. FRONTEND ARCHITECTURE

**Stack:** React 18 + TypeScript + Vite; React Router; TanStack Query; Zustand (tiny UI state); react-hook-form + zod; Recharts; Tailwind with design tokens; Radix UI primitives; `@fontsource/inter`; Vitest + RTL; Playwright. **No CDN assets, no external network calls at runtime.**

**Key rules**
- `services/api.ts`: one typed fetch client (credentials, `X-Requested-With: profitpilot`, error normalisation to `ApiError{code,message,fieldErrors,requestId}`).

- Error boundaries per route; global ApiErrorToast; skeletons for every async panel.
- ₹ formatting: `Intl.NumberFormat('en-IN',{style:'currency',currency:'INR',maximumFractionDigits:0})`.
- Accessibility: Section 31.

# 10. BACKEND ARCHITECTURE

**Stack:** Python 3.11+ (see DECISIONS D8), FastAPI, Pydantic v2, SQLAlchemy 2 (create_all for prototype), SQLite (`data/profitpilot.db`), NumPy/pandas, scikit-learn (training only), slowapi, PyJWT, `passlib[argon2]` (demo personas use no password), structlog-style JSON logs, pytest, httpx.

**Layers**
- `api/` — routers, schemas, dependencies (`get_current_user`, `require_role`, `get_seller_scope`), error handlers, middleware (request-ID, secure headers, CORS, rate limit).
- `services/` — catalog, goal, simulation, verdict, intervention, reverse_pricing, diagnosis, explain, audit, demo, employee.
- `ml/` — `world.py` (ground truth; used only by data generation and tests), `train.py`, `inference.py` (NumPy-only evaluation incl. bootstrap ensemble), `calibration.py`, `registry.py`.
- `optimization/` — `candidates.py`, `constraints.py`, `objective.py`, `search.py`, `sensitivity.py`, `catalogue.py`.
- `database/` — `models.py`, `session.py`, `seed.py`.

**Non-functional:** p95 latency budget in Section 12; cold start < 5 s; idempotent reads; structured JSON logs with request ID; deterministic seeds (`SEED=20260928`); server refuses to start in `APP_ENV=demo` if the model file is missing.

# 14. ML MODEL ARCHITECTURE

**Philosophy:** interpretable, monotone where economics demands it, fast, honest. No deep learning.

## 14.1 Models (trained on synthetic data)
| # | Model | Target | Form | Key inputs | Constraints |
|---|---|---|---|---|---|
| M1 | **Demand** | P(order \| impression) | Binomial GLM / logistic (counts as weights) | ln(p/p_ref), ln(comp/p), rating, image_quality, ln(1+reviews), traffic share, category one-hot, seller_quality | price coef ≤ 0 |
| M2 | **Payment mix** | P(COD \| order, price) | Logistic | ln(p/p_ref), prepaid_incentive, category, zone_tier, price band | price slope ≤ 0 |
| M3 | **Delivery / RTO** | P(RTO \| shipped order, payment) | Logistic | COD flag, category risk, seller_hist, zone_tier | COD coef ≥ 0 |
| M4 | **Return** | P(return \| delivered, payment) | Logistic | COD flag, category fit risk, ln(p/p_ref), image_quality, pack_quality, seller_hist | pack_q ≤ 0, img ≤ 0 |
| M5 | **Lifecycle economics** | per impression / order / kept order / day | Deterministic event tree (§16) | M1–M4 + costs | – |
| M6 | **Intervention optimiser** | best feasible intervention | Exhaustive search on discrete grid (§15) | M1–M5 + goal + guardrails | – |
| M7 | **Diagnosis** | bottleneck ranking | Rule engine + z-scores vs comparables | funnel rates | – |

**Uncertainty:** B = 30 bootstrap resamples (resample SKU-days, stratified by category); store 30 coefficient vectors; inference evaluates all 30 vectorised → p10/p50/p90; store ECE per model.
**Recovering ground truth:** test asserts fitted elasticity within ±25% of hidden β and fitted argmax within ±₹15 of the world argmax (K-101).

## 14.2 Comparable-observation evidence
`n_comparable(price)` = weighted count of SKU-days, same category, ±10% price window, ±0.2 image-quality band. <30 → `NEEDS_EVIDENCE`.

## 14.3 Cold start
Category prior + shrinkage of the SKU slope toward the category slope; similarity transfers **priors only**. Model view shows "Evidence: category prior + N comparables". (P1) brand-new-SKU toggle deletes history to show the low-confidence path.

## 14.4 Explicitly not modelled
Personalised buyer pricing, competitor reaction, ranking feedback loops, platform ad revenue → **Production-data dependent**.

## 14.5 Model versioning
`model_registry.version = "pp-synth-1.0.0"`; every simulation/recommendation stores version + `data_hash`.

## 14.6 The 10 pipeline nodes
1 SKU + seller context → 2 Demand → 3 Payment mix → 4 Delivery/RTO → 5 Returns → 6 Lifecycle economics → 7 Counterfactual simulator → 8 Constraint optimiser → 9 Recommendation → 10 Explanation + confidence. Each node exposes `prediction`, `inputs[]`, `output_for_sku`, `confidence`, `interpretation`, `drivers[{name,direction,share}]`, and (technical) `model_type`, `n_train`, `calibration_error`.

# 15. OPTIMIZATION LOGIC

## 15.1 Candidate generation
`price grid` = corridor_low−20 … corridor_high+20 step ₹1 (outside corridor computed but flagged extrapolation, never recommended).
`interventions` catalogue:

| Id | Intervention | Effect | Cost | Applies when |
|---|---|---|---|---|
| `PRICE` | Price change | move along curve | – | always |
| `PACK_PROTECT` | Better protective packaging | pack_q +0.35, pack_cost +₹4 | ₹4/order | always |
| `PARCEL_REDESIGN` | Lighter/right-sized parcel | fwd −₹24, rev −₹24 | ₹0 | flag `volumetric_slab_penalty` |
| `LISTING_IMAGE` | Improve primary image/size chart | img +0.18 (severe +0.35) | ₹1,500 one-time, amortised 30 d | image_quality < 0.7 |
| `BUNDLE2` | Bundle of 2 | demand ×0.72, freight ×1.35 | inventory ×2/order | inventory ≥ 2×daily target×7 |
| `PREPAID_INC` | Prepaid incentive ₹{10,20,30} | COD share ↓ via −0.03·inc | inc×(1−COD)/order | always |
| `SOURCING` | Lower sourcing cost (what-if) | cost − x | not recommendable | reverse pricing only |
| `AD_BUDGET` | Ad cost per order | ads ± | – | P2 |
| `MARKDOWN_LADDER` | Planned markdown for Clear | price steps to recovery floor | – | mode = Clear |

Search = {PRICE} ∪ single interventions × price grid ∪ pairs × price grid (≈171 × ~40 ≈ 7k evaluations × 30 bootstrap members, NumPy-vectorised).

## 15.2 Constraints (each returns pass/fail + margin)
1. Contribution floor (mean ≥ target; risk-adjusted p10 ≥ target − ₹5 for "High confidence feasible").
2. Volume floor (mean orders/day ≥ min_orders).
3. Return/RTO cap (leakage = 1 − d(1−r̄) ≤ cap).
4. Corridor (bundle: unit-equivalent price).
5. Max price move (|p−p_current|/p_current ≤ 12% per step).
6. Inventory (orders/day × units/order × 14 d ≤ inventory, unless Clear).
7. Cash (working capital ≤ cash_limit).
8. Confidence (≥ Medium to recommend; Low → `NEEDS_EVIDENCE`).
9. No buyer-level pricing (structural).

## 15.3 Verdict logic
```
price_only = search over PRICE with all constraints
if comparables < 30 or best.confidence == Low: NEEDS_EVIDENCE
elif price_only has feasible set: PRICE_WORKS → argmax of mode objective
elif diagnosis.top == non-price bottleneck (strength ≥ threshold) and price gap normal: NOT_A_PRICE_PROBLEM
else: PRICE_INFEASIBLE → intervention search, ranked (feasible → near-miss ≤10% shortfall → violators ✗)
```
If a much stronger non-price intervention exists alongside a feasible price, `PRICE_WORKS` still shows "Also consider" (max 1).

## 15.4 Objective by seller mode (shown in UI)
`Π_day` = expected retained contribution/day, `σ_day` = (p90−p10)/2.56, `WC` = working capital, `inv_loss` = expected unsold-stock loss.
- **Margin:** `J = Π_day − λσ_day`, λ = 1.0
- **Growth:** `J = Π_day − λσ_day + μ·orders_day`, μ = ₹4/order
- **Cash:** `J = (Π_day − λσ_day) / WC`
- **Clear:** `J = −(inv_loss) + ν·units_cleared_by_horizon − λσ_day`, recovery floor (cost+freight) replaces target contribution, horizon 30 days, reports days-to-clear (see D6 for exact implementation)
Ranking: J, ties → lower uncertainty → fewer changes.

## 15.5 Working capital (Illustrative cycle days `T_deliv=5`, `T_settle=7`, `T_return_loop=18`)
```
WC = orders_day·(cost·n + pack + fwd)·(T_deliv+T_settle) + returns_day·(cost·n)·T_return_loop + inventory_units·cost·n
```
(first two terms gate the cash constraint; the inventory term is reported as capital tied and added in Cash/Clear modes — see D3.)

## 15.6 Sensitivity analysis (P0)
`/recommendation` returns `sensitivity`: re-run the verdict with elasticity β ±50%, COD-slope ±50%, return-rate offset ±50%, freight ±50%; report whether the **intervention type** changes ("Recommendation is sensitive to: return-rate assumptions" / "Robust across ±50% on elasticity and COD effect").
# 16. MATHEMATICAL FORMULAS (must be implemented)

**16.1 Lifecycle probabilities**
```
q(x,p)   = σ(a_cat + β_cat·ln(p/p_ref) + γ1(rating−4) + γ2(img−0.5) + γ3·ln(p_comp/p) + …)   # order per impression (M1)
cod(x,p) = σ(c0 − κ·ln(p/p_ref) − 0.03·prepaid_inc)                                            # M2
z(x,p,m) = P(RTO | shipped, mode m) = σ(θ0 + θ1·1[m=COD] + θ2·cat_risk + θ3·seller_hist + θ4·zone)   # M3
r(x,p,m) = P(return | delivered, m) = σ(ρ0 + ρ1·1[m=COD] + ρ2·fit_risk + ρ3·(1−img) + ρ4·seller_hist − ρ5·pack_q + ρ6·ln(p/p_ref))   # M4
c        = P(cancel | order)
d(x,p)   = 1 − [cod·z(COD) + (1−cod)·z(PP)]
r̄(x,p)  = Σ_m w_m(1−z_m)·r_m / Σ_m w_m(1−z_m),  w_COD=cod, w_PP=1−cod
leakage  = 1 − d·(1 − r̄)
```
**16.2 Event-tree contribution per placed order**
```
v        = n·p/(1+GST) − PaymentFee(n·p) − PrepaidIncentive·(1−cod)
KeptVal  = v − n·C_prod − C_pack − C_fwd − C_ads
RetVal   = −(C_fwd + C_rev + n·C_restock + C_pack) − 0.5·C_ads
RtoVal   = −(C_fwd + C_pack)
Π_order  = (1−c)·d·(1−r̄)·KeptVal + (1−c)·d·r̄·RetVal + (1−c)·(1−d)·RtoVal − c·C_cancel
kept     = (1−c)·d·(1−r̄)
Π_kept   = Π_order / kept
```
**16.3 Daily and per-impression**
```
orders_day = impressions_day · q · demand_mult
Π_day      = orders_day · Π_order − amortised one-time costs
Π_imp      = q · Π_order − C_capital(p,x)/impressions_day
kept_orders_day = orders_day · kept ; GMV_day = orders_day·n·p ; NMV_day = kept_orders_day·n·p
C_capital = WC · (annual_cost_of_capital/365)
```
**16.4 GST handling.** `gst_rate` (default 5% for apparel ≤ ₹2,500/pc, 18% above — Research-backed per PDF §2.2), `gst_is_cost` (default true), `price_is_tax_inclusive` (default true). Never hard-code 5%; read from a `tax_rules` table keyed by category + price threshold. (Research-backed: apparel GST slabs.)
**16.5 Risk-adjusted contribution:** `Π_day^RA = mean − λ·σ`, σ from the 30-member bootstrap; report p10/p50/p90.
**16.6 Elasticity note:** the textbook rule isn't used as a decision rule; the engine differentiates numerically (Δp = ₹1), displays `ε_local = d ln orders / d ln p` and `dΠ_day/dp`; a test asserts the price at `dΠ_day/dp = 0` equals the grid argmax (±₹1).
**16.7 Confidence:** §20. **16.8 Reverse-pricing required price:** §17.

# 17. REVERSE-PRICING LOGIC

1. **Price-only test** over the grid inside corridor & move cap; record `best_price_option` + per-constraint shortfalls.
2. **Required price** `p*` by bisection where `Π_kept(p*) ≥ target` (even outside corridor) → "you'd need ₹X, above the ₹Y market ceiling" (computed, not asserted).
3. **Volume check at p\*** — if `orders_day(p*) < min_orders`, explain which constraint binds.
4. **Lever search** — single interventions and pairs across the grid; feasible first, else near-misses.
5. **Required-change solver** — for `SOURCING` solve minimum Δc, for `PARCEL/PACK` solve required freight reduction → "You would need ₹X lower freight/sourcing" (**Illustrative target, not a recommendation**).
6. **Rank** feasible by `J` (§15.4). Return top 6.
7. **Narrative builder** (template): rejected → `"{option} rejected: {binding constraint} ({actual} vs {required})."`; winner → `"{winner} works because {driver decomposition}."`

# 18. INTERVENTION RECOMMENDATION LOGIC

- Every option returns `InterventionResult` `{id, label, params, metrics{…each p10/p50/p90}, constraint_results[], status FEASIBLE|NEAR_MISS|VIOLATES, shortfall, tradeoffs[2], why[1–2], confidence, evidence_n, label:"Estimated"}`.
- **Status rules:** FEASIBLE if all hard constraints pass at mean; NEAR_MISS if only contribution/volume miss by ≤10% of target; VIOLATES if a guardrail (return cap, corridor, inventory, cash) fails.
- **Tradeoff generator** picks the two largest signed deltas vs current state.
- **Rejected options** (collapsed) with reasons (e.g. prepaid incentive: "cuts COD share 54%→39% but lowers contribution per kept order ₹71→₹61").
- **Recommendation-only:** CTA is **Save recommendation**; "Applied (simulated)" is a demo state.

# 19. EXPLAINABILITY SYSTEM

| Field | Template | Source |
|---|---|---|
| **WHAT** | "Increase price from ₹{p0} → ₹{p1}." / "Bundle 2 units at ₹{price} with upgraded packaging." | chosen option |
| **WHY** | "{orders_delta}% fewer orders but +₹{Δkept} per kept order and {Δleak}pp lower return/RTO cost, so contribution/day rises ₹{ΔΠ}." | event-tree delta decomposition |
| **EXPECTED IMPACT** | "+₹{ΔΠ_day}/day retained contribution (range ₹{lo}–₹{hi}); orders {o0}→{o1}/day." | p10/p50/p90 |
| **RISK** | "{confidence} confidence: only {n} comparable observations near ₹{p1}." + top-2 uncertainty drivers | §20 |

**Event-tree decomposition** (`GET /model/explanation`): branch probabilities and per-branch ₹ (kept/returned/RTO/cancelled) + **counterfactual attribution** of Δ contribution into price effect on demand, COD-mix effect, RTO effect, return effect, freight effect, packaging cost — computed by sequentially switching one block at a time (fixed order), reported as ₹/order and normalised shares.
**UI:** "Why?" drawer = (1) sentence answers, (2) stacked event-tree bar for current vs recommended, (3) drivers list, (4) "Show technical detail".

# 20. UNCERTAINTY SYSTEM

**Never show a bare number.** Every Estimated metric renders `₹61 (₹57–₹65)` + ConfidenceBadge.
```
n_eff = kernel-weighted comparable SKU-days within ±10% price window
gap   = max(0, (price − observed price range)/observed range width)   # % extrapolation
width = (p90 − p10)/|p50| ; ece = calibration error of relevant models
High   : n_eff ≥ 1000 and gap = 0 and width ≤ 0.15 and ece ≤ 0.03
Low    : n_eff < 300 or gap > 15% or width > 0.40 or ece > 0.06
Medium : otherwise
```
- **Low** → recommendation replaced by "Run a controlled test first" + `NEEDS_EVIDENCE` if `n_comparable < 30`; no moves > 5% suggested at Low.
- **Uncertainty drivers:** bootstrap variance decomposition over {elasticity, COD slope, RTO, return, freight}; UI shows "Recommendation is sensitive to return-rate assumptions." + bars (top 4).
- **Data-label chips** on every panel: Synthetic / Illustrative / Estimated.
- Model view + Employee Experiments explain the production path: observational baseline → randomised price experiments (2–3 arms, opt-in, min sample, rollback) → doubly robust evaluation (roadmap).

| Low confidence | Yellow banner: "Directional only" + narrower suggested move |
| No feasible solution | "No feasible solution under your constraints" + "Relax which constraint?" chips |
| Session expired | Redirect to login with toast |
| Offline | `navigator.onLine` banner |

# 25. TESTING STRATEGY

**Backend unit:** event-tree probability sum = 1, per-branch values, golden numbers (K-101 @₹399 → 22.8 orders, per_kept ≈ 71.3); constraints pass/fail/margins; optimiser verdicts; `dΠ/dp = 0` at argmax; GST table; working capital; NaN/negative rejection.
**Model tests:** probability ranges; monotonicity (orders ↓ in price, COD ↓ in price, leakage ↑ in COD, RTO ↑ in COD, return ↓ in pack/image quality); missing values → priors; extreme prices → Low confidence; recovery of β (±25%) and argmax (±₹15); ECE ≤ 0.03; determinism.
**API tests:** 422 shapes; unknown fields rejected; 401/403; seller isolation → 404 + audit row; 429; route-role matrix; every route has an auth dependency; customer serializer key check.
**Frontend:** form validation, slider keyboard, chart tooltip, verdict rendering, TruthLabel presence, ₹ formatting.
**E2E (≥8 steps):** demo-login → select K-207 → set goal → simulator (keyboard slider) → "Can price reach my goal?" → assert banner + 3 interventions → reverse pricing → save recommendation + History row; plus isolation 404, employee aggregates, diagnosis on K-118.
**Performance:** curve < 300 ms cold / < 50 ms cached; recommendation < 1 s. **Accessibility:** axe-core on 5 key pages.
