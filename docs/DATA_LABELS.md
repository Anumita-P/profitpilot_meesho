# DATA_LABELS.md — what every number in ProfitPilot is allowed to claim

The product's honesty rule is enforced in code, not in a footnote. This file is the contract:
which label every number-bearing surface carries, what each label means, and what may never appear.

---

## 1. The three labels

| Label | Meaning | Example surfaces |
| --- | --- | --- |
| **Synthetic** | Produced by the offline simulator (`backend/app/ml/world.py`), seed `20260928`. Not observed, not measured, not from any real seller or order. | catalogue rows, funnel counts, event-tree probabilities, employee fleet replay, audit counts |
| **Illustrative** | An *input assumption* the prototype had to choose. A real deployment would read it from the seller's ledger. | unit cost, packaging cost, forward/reverse freight, ad spend, payment fee, GST rate, cost of capital, cycle days (`T_deliv=5`, `T_settle=7`, `T_return_loop=18`), inventory horizon (14 days), write-down rate (35%) |
| **Estimated** | Model output. Always shown with a p10–p90 range and a confidence badge. | contribution per kept order, contribution/day, orders/day, order probability, COD share, RTO, return rate, leakage, NMV/day, working capital, elasticity, intervention metrics, diagnosis expected effect |

**Never a bare Estimated number.** Every Estimated value ships as *value + p10–p90 + confidence
badge*. `RangeNumber`, `MetricBlock` and `ConfidencePill` (`frontend/src/components/ui.tsx`) make it
hard to render one any other way, and the API always returns the band (`{"p10","p50","p90"}`).

---

## 2. Where the labels appear

| Screen / payload | Labels carried |
| --- | --- |
| Login | Synthetic banner; the one allowed Meesho figure (see §4) |
| Catalog | row-level `label: "estimated"`; status pills; each number has a range |
| Snapshot | Estimated (hero + secondary), Illustrative (waterfall costs), Synthetic (last observed day) |
| Simulator | Estimated (curves, point, constraints, event tree, sensitivity); Illustrative (goal form, intervention assumptions) |
| Recommendation | Estimated (recommendation, alternatives, rejected reasons, sensitivity); Illustrative (goal); guardrail bar |
| Reverse pricing | Estimated (solutions, required price); Illustrative (objective weights, cost-reduction note) |
| Diagnosis | Synthetic (funnel, bottleneck evidence), Estimated (expected effect, price-only comparison) |
| Model pipeline | Synthetic (metrics, recovery report); each node names its model type |
| Employee views | Synthetic — simulated rollout on every tab; audit counts are real counts of synthetic events |
| Customer listing | Synthetic; delivery estimate is explicitly marked Illustrative |
| API responses | `label` / `data_label` field on every number-bearing payload (`/api/health` → `synthetic`) |

The API is the source: the browser renders the label the server sent. A screen cannot claim
"Estimated" for something the backend labelled synthetic, or vice versa.

---

## 3. What is never claimed

* No Meesho data, no Meesho internal systems, no Meesho APIs. Every seller, listing, order, cost,
  buyer and reviewer is generated by `scripts/generate_data.py`.
* No causal claim from the fleet view: the employee rollout is a *simulation with a heuristic
  adopt rule*, and the experiments tab labels its three rows "Synthetic — never run on real traffic".
* No measured outcome anywhere. Nothing in the product was A/B tested; the word "uplift" is always
  attached to a simulated rollout, never to live traffic.
* No personalised pricing. The engine prices a listing, not a person: `no_buyer_pricing` is a
  structural constraint that always passes, and the customer view states it in plain words.
* No precision theatre. Confidence labels are computed from comparable evidence (`n_eff`), band
  width and calibration error, and the rule is shown on hover.

---

## 4. The single allowed real number

One company-reported figure may appear, once, as motivation — and only in its correct form:

> Meesho's company-reported FY26 NMV was about 58.8% of GMV — i.e. roughly two-fifths of what a
> buyer pays is not product value.

It is rendered in the About footnote (`AboutFootnote` in `frontend/src/components/ui.tsx`) and
nowhere else. It is never used as an input, a benchmark, or a target in any computation.

**Banned strings** (checked by `grep -r` before each release, and asserted absent in the UI copy):
`1,842 comparable listings`, `fit = 53%`, `70% of orders from feed`, `₹70 crore`,
`10× capital turns`, `64% delivery`.

---

## 5. Labelling rules that came out of review

1. **A range is not optional.** Any new metric added to an API response must carry p10/p50/p90, or be
   explicitly typed as an input (Illustrative) or a simulated count (Synthetic).
2. **The label follows the weakest link.** A panel that mixes a fitted estimate with an input cost is
   labelled Estimated (the estimate is the weaker claim) and the inputs are named in the note.
3. **Confidence is a rule, not a vibe.** `n_eff ≥ 1000 ∧ gap ≤ 0 ∧ width ≤ 0.15 ∧ ECE ≤ 0.03` → High;
   `n_eff < 300 ∨ gap > 0.15 ∨ width > 0.40 ∨ ECE > 0.06` → Low; otherwise Medium. Low confidence is
   never recommended.
4. **Zero is a result.** A simulated adoption rate of 0% or a blocked-recommendation count is shown
   as-is with the reason, never smoothed into something more flattering.
5. **Rejections keep their reason.** Every option that fails states which constraint it failed
   (`considered_and_rejected[].reason`) — the UI never hides a rejected option behind a click.
